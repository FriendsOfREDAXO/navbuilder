# URL addon integration — design spec

Date: 2026-08-15
Status: approved design, pre-implementation

## Goal

A navigation item can point at a dataset URL generated by the `url` addon
(FriendsOfRedaxo/url). One item = one hand-picked dataset URL. No dynamic
"expand a profile into children" item — deliberately out of scope until a real
need shows up.

The integration must feel first-class: picking a URL is as easy as picking an
article today, and everything follows the existing NavBuilder rules — the
server is authoritative, references are stored as stable ids, names and URLs
are resolved at render time, never cached.

## Non-goals

- Dynamic profile items (one nav entry per dataset, rendered at request time).
- A generic "custom item type" extension API. The url addon is integrated
  directly as an optional peer; an abstraction gets extracted only when a
  second real consumer exists.
- A separate bridge addon.

## 1. Schema & data model

New schema-v2 item type `url`, alongside `article` / `link` / `media` / `text`:

```json
{"id":"a1b2c3d4","type":"url","profileId":3,"dataId":17,"label":"","target":"_blank","hiddenIn":[],"children":[]}
```

- **Identity is `profileId` + `dataId`, nothing else.** Generator row ids in
  `rex_url_generator_url` are rewritten on URL regeneration and the URL string
  changes when slugs change, so neither may be stored — the same philosophy as
  `article` items storing only the article id.
- **No clang is stored.** The url addon generates per-clang rows; the renderer
  resolves for the clang being rendered.
- `label` is an editorial override only, never a cache. Empty label = resolved
  name at render time.
- `target` behaves exactly like on `link` / `media` items.
- `hiddenIn` works as on every other type.
- `Navigation::normalizeItems()`: `profileId` and `dataId` must both be
  numeric and ≥ 1. Strict mode rejects the payload; lenient mode drops the
  item with a warning, mirroring the non-numeric article-reference handling.
- **No schema version bump.** v2 gains a type. A downgrade to an older
  NavBuilder version would drop `url` items with a warning on the next save;
  this is accepted and noted in the CHANGELOG.

## 2. Rendering & resolution (`Renderer::buildTree()`)

New branch for `'url' === $type`:

1. If the url addon is not available (`rex_addon::get('url')->isAvailable()`
   is false) → skip the item and its subtree, log one warning. Stored data
   stays intact.
2. Resolve the generated URL for (`profileId`, `dataId`, ctx clang). No
   matching row (profile does not generate that clang, dataset deleted) →
   skip, exactly like a deleted article. Lookup preference: the url addon's
   `UrlManager` API if it covers profile+data+clang lookup, otherwise one
   indexed SELECT on `rex_url_generator_url`. The exact call is verified
   against the Gastrozentrum instance at implementation time.
3. `label` falls back to the generator row's stored seo title (kept current by
   the url addon on dataset changes — render-time resolution, not a NavBuilder
   cache), then to the URL itself.
4. The `absolute` option is honored; whether the stored `url` column is
   already absolute (and must be relativized for the default case) is verified
   at implementation time.
5. `active` is true when the current request resolves — via the url addon —
   to the same profile + dataset. `activePath` bubbles up through
   `hasActive()` unchanged.

Node shape: resolved nodes gain `profileId` / `dataId` (int, `null` on every
other type) so project fragments can branch on them, mirroring how `article`
nodes expose `articleId` / `categoryId`. The doc block at the top of
`Renderer.php` is extended accordingly.

## 3. Backend API (picker search)

A second small `rex_api_function` (`lib/UrlApi.php` or equivalent),
`rex-api-call=navbuilder_urls`, mirroring `Api.php` exactly: backend-only
(`$published = false`), `navbuilder[]` permission required, CSRF-protected
with JSON responses in every case including failures.

Request / response:

```
GET index.php?rex-api-call=navbuilder_urls&q=…&clang=…&profile=…&_csrf_token=…
→ {"items":[{"profileId":3,"dataId":17,"name":"Pizzeria Toni","profile":"restaurant","url":"/restaurants/pizzeria-toni/"}]}
```

- Searches `rex_url_generator_url` for the given clang: seo title `LIKE` and
  url `LIKE`, with the same LIKE-escaping and `LIMIT 30` pattern as
  `Api::searchArticles()`.
- `profile` (optional) filters by profile **namespace** — the human-readable
  key (e.g. `restaurant`) that also serves as the badge text in results.
- The list of available profiles (id + namespace) ships in the
  `NavBuilderInit` payload, so the filter dropdown needs no extra request.

Page-load enrichment: `pages/menus.php` decorates url items the same way it
decorates article items — `_label`, `_url`, `_exists`, plus `_profile` for the
badge. All `_`-prefixed, all transient, all stripped by `clean()`.

## 4. Editor (assets/navbuilder.js + pages/menus.php)

- Palette gains a **URL** entry, rendered only when the init payload says the
  feature exists (`NavBuilderInit.features.url`, set server-side from
  `rex_addon::get('url')->isAvailable()`). The client never probes for the
  addon itself.
- The item body reuses the existing article autocomplete pattern (same
  combobox/ARIA structure): one search field; each result shows the dataset
  **name**, the profile namespace as a badge, and the URL underneath.
- A profile filter dropdown renders only when more than one profile exists —
  single-profile sites see zero extra chrome.
- Selected state: resolved name with URL hint (like the article `_url` hint),
  a label-override input whose placeholder is the resolved name, and a target
  select. `_exists: false` shows the same warning flag as a deleted article.
- `EDITABLE` gains `profileId`, `dataId`, `_profile`; `clean()` keeps
  `profileId` / `dataId` in the posted payload and strips every `_` field, as
  its contract requires.
- No rendered string literals: every user-visible string comes from
  `NavBuilderInit.i18n`, with lang keys added to `de` and `en` in sync
  (German primary).

## 5. Degradation & lifecycle

- `package.yml`: the url addon becomes a **suggestion**, never a requirement.
- url addon uninstalled or deactivated later:
  - Editor: palette entry disappears; existing `url` items still render in the
    tree, flagged "url addon missing", and remain saveable — data is never
    lost or repaired away.
  - Frontend: items are skipped with a log warning (section 2, step 1).
- No DB migration, no changes to `update.php` or `Navigation::migrateAll()`.

## 6. Testing

- **PHP** (`tests/php/`, pure schema surface as today):
  `normalizeItems` for the `url` type — valid item passes through, strict
  mode rejects non-numeric/missing ids, lenient mode drops with warning, all
  unrelated fields stripped.
- **JS** (`tests/js/`, `node --test`): `clean()` keeps `profileId` / `dataId`
  and strips `_label` / `_url` / `_exists` / `_profile` on url items.
- **DB / render paths**: exercised manually in the Gastrozentrum instance
  (symlinked live install), as is the norm for this repo — including the
  `UrlManager` lookup, the absolute-URL question, and the `active` detection.

- CHANGELOG.md entry, including the downgrade note from section 1.
