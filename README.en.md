# NavBuilder

*🇩🇪 [Deutsche Version](README.md)*

Build navigations in the REDAXO backend via drag & drop, output them anywhere through
overridable fragments.

- Backend editor: recursive tree, native HTML5 drag & drop, keyboard-operable move buttons,
  per-item "insert below", core linkmap + article autocomplete, live-enriched article names
  (renaming an article never leaves a stale label behind).
- Frontend: `rex_navbuilder::render()` (HTML via fragments) and `rex_navbuilder::tree()` (array),
  plus the `REX_NAVBUILDER[name=…]` output filter for templates/modules.
- No build step: Vue 3.5.13 is vendored as `assets/vue.global.prod.js` (no CDN), loaded only on
  the addon's own backend page.

## Requirements

- REDAXO `^5.18`
- PHP `>=8.1`
- `structure` addon `^2.9`
- Optional: the [`url`](https://github.com/FriendsOfREDAXO/url) addon — for the `url` item type
  only. Deliberately not a dependency: without the addon that type is simply absent, everything
  else works unchanged.

No `yform`, no `phpmailer` dependency (both dropped in 2.0 — see Changelog).

## Install

Install/activate as usual via the package manager. A `rex_navbuilder_navigation` table is
created (`id`, `name`, `structure`, `structure_legacy`, `updated_at`).

## Upgrading from 1.x

Activating 2.0 over an existing 1.x install runs `update.php`, which:

1. Adds the new columns (`structure_legacy`, `updated_at`) and a `UNIQUE(name)` index (skipped
   with a log warning if duplicate names already exist — `Navigation::save()` still guards
   names going forward).
2. Migrates every stored navigation from the v1 shape
   (`{"type":"intern","text":"Page [12]","href":"12"}`) to the v2 schema (below), mapping
   `intern → article`, `extern → link`, `group → text`. The v1 `text` field (an article-name
   cache that went stale on rename) is dropped — the frontend never read it anyway, since names
   and URLs were already resolved live at render time.
3. Backs up the pre-migration JSON into `structure_legacy` (only if that column is still empty,
   so re-running never clobbers the original).

The migration is **idempotent**: rows already carrying `"v":2` are skipped, so `update.php` can
be run any number of times. `href` values that aren't numeric on a v1 `intern` item are dropped
and logged via `rex_logger` rather than migrated as garbage. If the migration had to drop items,
the update message names the count (details in the system log). Before updating, existing names
are preflighted: names longer than 191 characters abort the update with a clear message (shorten
them first), non-slug names are reported in the system log — they keep working via
`rex_navbuilder::render()` but cannot be addressed with `REX_NAVBUILDER[name=…]`. Nothing here touches the frontend
API — `render()`/`tree()`/the deprecated shims all keep working during and after the migration.

## Data model (v2)

```jsonc
{
  "v": 2,
  "maxDepth": 3,                       // optional, absent = unlimited (hard cap: 10)
  "items": [
    { "id": "a1b2c3d4", "type": "article", "articleId": 12, "clang": null, "children": [],
      "label": "optional editorial override", "hiddenIn": [2] },
    { "id": "e5f6a7b8", "type": "link", "url": "https://example.com", "label": "External",
      "target": "_blank", "children": [] },
    { "id": "b1c2d3e4", "type": "media", "file": "brochure.pdf", "label": "Brochure",
      "target": "_blank", "children": [] },
    { "id": "d3e4f5a6", "type": "url", "profileId": 3, "dataId": 17,
      "target": "_self", "children": [] },
    { "id": "c9d0e1f2", "type": "text", "label": "Service", "text": "<p>…</p>",
      "children": [] }
  ]
}
```

`article` items carry the article id only; name and URL are resolved at render time. A `label`
on an `article` item is a deliberate override, never a cache — omit it to always show the
current article name.

`media` items carry the mediapool file name only. URL and existence are resolved at render time
via `rex_media::get()`; without a `label` the file name is shown. A deleted file disappears from
frontend output and is flagged in the backend — exactly like a deleted article.

To keep it from getting that far, NavBuilder guards both references on deletion: an article still
used in a navigation cannot be deleted (the error message links the affected navigations), and the
mediapool reports a still-referenced file as "in use" and refuses the deletion as well.

`url` items point at a dataset URL generated by the [url addon](https://github.com/FriendsOfREDAXO/url)
and need that addon (see below). They carry `profileId` and `dataId` only — address and name are
resolved at render time (name: the generator's SEO title, falling back to the path). As everywhere,
a `label` is an editorial override, never a cache.

`text` items are purely structural (formerly `group`, see the changelog). Next to `label` they
can carry an optional `text` field holding **HTML**. The two are independent: `text` is always the
body, never a stand-in for the label — an item without a `label` keeps an empty one (the backend row
shows a markup-free excerpt instead). The old type name `group` is mapped to
`text` on read, so stored data keeps working untouched.

Email and phone entries are plain `link` items (`mailto:…` / `tel:…`) — the editor's detection
only builds the url, it adds nothing to the data model.

### Dataset URLs (url addon)

The [url addon](https://github.com/FriendsOfREDAXO/url) is an **optional peer, never a
requirement**: the `url` type only shows up in the backend when the addon is installed.

Only the canonical dataset URL resolves. Rows the url addon keeps as a dataset's appended
sub-URLs (`is_user_path`/`is_structure`, e.g. a gallery page below a detail page) appear neither
in the picker nor in the output.

Resolution is **per language**: if there is no generated URL for the language being rendered —
because the profile does not generate it, or the dataset is gone — the item is skipped together
with all its children, exactly like a deleted article. `active` applies when the request path
matches the generated URL (a trailing `/` makes no difference).

In the backend the picker searches every generated URL of the language selected in the backend —
by name and address; each hit shows the name, the profile namespace as a badge and the path. With
more than one profile, a profile filter sits above the search.

Uninstalling the url addon later keeps stored `url` items: the backend flags them with "URL addon
not available" and they stay editable and savable (converting them to another type included), the
frontend skips them — with exactly one warning in the system log per request, not one per item.

### Per-language visibility

Every item — whatever its type — may carry an optional `hiddenIn: [clang_id, …]`: the languages
it is **not** rendered in. An absent key or an empty list means "visible everywhere" (empty lists
are dropped on save). At render time a hidden item is skipped together with all its children, and
that happens **before** the `rex_article::status` check — the two filters are independent: an
offline article still disappears everywhere, `hiddenIn` only controls the language. In the backend
the languages show up as a row of chips in the edit form, but only when there is more than one
language; affected rows carry a small hint with the language codes in the tree.

### Maximum depth

The structure JSON root may carry `maxDepth`: the maximum nesting depth of this navigation. `1`
means flat — entries without children; an absent key falls back to the global hard cap of 10 levels.

The limit is **editorial policy and therefore an administrator's call**: only admins see the field,
and only their saves write the value. On a save by anyone else a posted `maxDepth` is ignored and
the stored value is carried over (for new navigations: none) — so the policy cannot be lifted by a
tampered form.

The editor enforces it live (the indent button is disabled, drop-inside is refused), but the server
is authoritative: a tree nested deeper than the limit is **rejected** on save (naming both the limit
and the actual depth), never silently flattened — the global 10-level cap included.

## Backend usage

*Menus → NavBuilder*: create a navigation, drag articles/links/media/datasets/text into the tree (or use the
up/down/indent/outdent buttons — full keyboard path, `aria-label`ed). The **+** button on a row
inserts a new sibling directly below that item (and below its children) instead of appending it
at the end. Deleted or offline articles are flagged in the tree instead of silently breaking the
navigation; they're excluded from frontend output. Use **Duplicate** in the list to branch a
navigation (e.g. main nav → footer nav) without rebuilding it.

The link form is a **single field** for url, email address or phone number. What you
type is detected live and shown as a small indicator inside the field (Link / Email / Phone): a
bare address becomes `mailto:…`, a phone number becomes `tel:…` (digits and a leading `+`
survive), a bare hostname (`example.com`, `sub.example.ch:8080`) or a `www.` start gets `https://`
prepended. Anything else containing a `/` is left byte-untouched — `downloads/broschuere.pdf` is a
valid relative target, and `example.com/path` gives up the convenience so no path can break.
Relative targets (`/kontakt/`,
`#top`, `?p=1`, `//cdn…`) and anything with its own scheme are stored as typed. Editing such an
entry again shows the bare address/number with the matching indicator — unless detection would
not rebuild the scheme identically (e.g. `tel:0800-REDAXO`), in which case the full url stays. "Open in a new window"
(`target="_blank"`) appears for real urls only. Detection is an input aid — the same scheme
allowlist is still checked client-side and, authoritatively, on the server.

**All types convert into each other in place**: the edit form has an
**Article | Link | Media | URL | Text** switch at the top (the URL button only with the url addon
installed — or when the item already is one). Switching only changes what the form shows —
the conversion is committed on *Apply*, keeping `id`, label, language visibility and all children
while dropping the other types' fields. A conversion without a target (no article picked, no
address typed, no file chosen, no dataset chosen) is refused with an inline message instead of losing the item and
its children; converting **to** text needs no target, since both its label and its body are
optional. Converting a text item that has a body shows a standing hint next to the switch that the
body will be discarded on apply — it is the one thing a conversion cannot carry over. *Cancel*
restores the type **and** the body.

**Media** is picked through the mediapool (the *Choose file* button, the same popup path the core
widget uses); the file name field is deliberately readonly. Like links, media items offer "open
in new window" (`target="_blank"`). **Dataset URLs** are picked through a search field (details
above under *Dataset URLs*), likewise with "open in new window" and a field for the custom label.
**Text** items have a textarea for
HTML next to their label — see the warning under *Fragment overrides*.

The edit form also shows the item's internal `id` (small, greyed, bottom right) — that is the
handle for per-item styling, see below.

Names are slugs — `Navigation::save()` only accepts `[a-z0-9_-]+`. This matches the
`REX_NAVBUILDER[name=…]` output filter's regex exactly; any other name would save but could
never be addressed by a snippet.

The snippet to embed a navigation (`REX_NAVBUILDER[name=…]`) is shown next to each entry in the
list.

### Permissions (multisite / multidomain)

Three layers, all in the role editor under *Users → Roles*:

- **`navbuilder[]`** (page permission): opens the NavBuilder page — prerequisite for
  everything else.
- **Navigations** (multi-select): which navigations the role may **edit**. The selection is
  bound to the navigation itself (not its name), so renaming never changes permissions.
  *"Edit all navigations"* allows editing every navigation — but still no creating or
  deleting.
- **`navbuilder[manage]`** (option): **create, duplicate and delete** navigations — includes
  editing all of them. Admins have this implicitly.

This maps the multisite scenario directly: site administration gets `navbuilder[manage]`,
each domain's editors get a role with exactly their navigations. Editors with no selection
see an empty list. Deleting a navigation automatically removes it from all roles. All checks
run server-side — the hidden buttons are convenience only.

## Frontend API

```php
// Render through fragments/navbuilder/{navigation,item}.php:
echo rex_navbuilder::render('main');

// Override the fragment and cap nesting depth:
echo rex_navbuilder::render('main', ['fragment' => 'project/nav.php', 'depth' => 2]);

// Resolved tree as an array, for custom rendering:
$tree = rex_navbuilder::tree('main');

// In template/module output:
REX_NAVBUILDER[name=main]
```

`render()`/`tree()` options: `clang`, `currentId` (defaults to the current article),
`depth` (0 = unlimited), `absolute` (use `rex_yrewrite` full URLs when available), plus
`fragment`/`itemFragment`/`class` for `render()`.

Every node returned by `tree()` (and passed to fragments):

| key | type | notes |
|---|---|---|
| `id` | string | stable internal id, for `:key`/diffing and per-item styling |
| `type` | string | `article` \| `link` \| `media` \| `url` \| `text` |
| `label` | string | article name, file name, dataset title, override, or link/text label |
| `url` | `?string` | `null` for `text` items |
| `text` | `?string` | raw HTML, only for `text` items |
| `file` | `?string` | mediapool file name, only for `media` items (e.g. to branch on the extension) |
| `articleId` | `?int` | only for `article` items |
| `categoryId` | `?int` | category of that article (`0` at root level, the category itself for its start article); `null` for every other type |
| `profileId` | `?int` | url addon profile, only for `url` items |
| `dataId` | `?int` | dataset id within that profile, only for `url` items |
| `target` | `?string` | only for `link`, `media` and `url` items with an explicit target |
| `online` | bool | always `true` — offline/deleted articles are filtered out already |
| `active` | bool | points at exactly the current article (for `url` items: at the requested path) |
| `activePath` | bool | active, an ancestor of it, or has an active descendant |
| `depth` | int | 1-based |
| `children` | list | same shape |

## Fragment overrides

Copy either file into your project to override it — REDAXO's fragment lookup picks up the
project copy automatically:

```
fragments/navbuilder/navigation.php  → project/fragments/navbuilder/navigation.php
fragments/navbuilder/item.php        → project/fragments/navbuilder/item.php
fragments/navbuilder/text.php        → project/fragments/navbuilder/text.php
```

`navigation.php` and `item.php` travel through `render()`'s vars, so an override applies at every
nesting level, not just the top one. All output in the shipped fragments goes through
`rex_escape()` — **with one exception**:

> ⚠️ `text.php` prints a `text` item's `text` field **raw**. That is deliberate: it is
> editor-authored HTML, exactly like the content of a module textarea, and escaping it would
> defeat the point of the field. So it carries the same trust boundary modules do — only backend
> users with access to the navigation can write it. If you do not want that, override `text.php`
> and escape there.

### An editor for the text field (`NAVBUILDER_INIT`)

The textarea always carries the class `navbuilder-text-input`. The `NAVBUILDER_INIT` extension
point can append another class, e.g. to attach a WYSIWYG editor:

```php
// project/boot.php
rex_extension::register('NAVBUILDER_INIT', function (rex_extension_point $ep) {
    $init = $ep->getSubject();
    $init['textClass'] = 'tiny-editor';   // applied to the textarea
    return $init;
});
```

The extension point receives the complete `window.NavBuilderInit` array right before it is
written into the page as JSON (see the header of `pages/menus.php`).

### Styling single items

Every node carries enough identity for an override to branch on a single entry — without
matching labels, which change. `id` is the stable internal id (shown in the backend edit form),
`articleId` and `categoryId` come from the resolved article:

```php
// project/fragments/navbuilder/item.php
$item = (array) $this->getVar('item', []);
$classes = ['nav__item', 'nav__item--' . rex_escape($item['id'])];          // this exact entry
$classes[] = 'nav__item--cat-' . (int) ($item['categoryId'] ?? 0);          // whole category
$highlight = 22 === ($item['articleId'] ?? null);                           // one article
```

`categoryId` is `null` for `link`, `media`, `url` and `text` items, so cast before comparing;
`url` items carry `profileId`/`dataId` instead — the stable handle for a single dataset.

## Deprecated API

Kept as thin shims, no removal planned before a future major:

| deprecated | use instead | why |
|---|---|---|
| `rex_navbuilder::get($name)` | `rex_navbuilder::render($name)` | hardcoded `rex-*` classes are gone; output now comes from fragments |
| `rex_navbuilder::getStructure($name)` | `rex_navbuilder::tree($name)` | nodes gained `activePath`, `online`, `url`; offline articles are now filtered consistently (v1's two entry points disagreed on this) |
